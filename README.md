# Mars Mission

A planning and simulation game in which you run a Mars exploration Program on a budget. Vocabulary is in [GLOSSARY.md](GLOSSARY.md), the rules are in [docs/game-design.md](docs/game-design.md) and the decisions behind them are in [docs/adr/](docs/adr/).

## Play

You need [Node.js](https://nodejs.org/) 24 or later. From the repository root, run:

```powershell
.\run.bat
```

You can also double-click `run.bat`. It installs what's needed, builds the game and opens it in your browser. The game is designed for a desktop monitor: 4K at 100% or 150% display scaling, or 1920×1080.

To try the latest phase, follow the [Phase 7 playtest guide](docs/playtest/phase-7.md). The [Phase 1](docs/playtest/phase-1.md), [Phase 2](docs/playtest/phase-2.md), [Phase 3](docs/playtest/phase-3.md), [Phase 4](docs/playtest/phase-4.md), [Phase 5](docs/playtest/phase-5.md) and [Phase 6](docs/playtest/phase-6.md) guides are kept as records of those phases, so some controls and numbers have changed since they were written. The [Status](docs/game-design.md#status) section of the design doc lists what each phase built and what changed after its playtest. Only the current guide's known seeds are tested, in `src/catalogue/playtestSeedsPhase7.test.ts`, and those tests move to the new guide with each phase. If tuning breaks one, find a new seed that gives the same story and update the current guide, because earlier guides are records and aren't updated.

Test fixtures go in `src/simulation/testCatalogue.ts` and `testHelpers.ts` for rule tests, which use round numbers so that balance changes don't break them. For tests of the game's actual balance, use `src/testing`. `realCatalogue.ts` has the real data files and a calm version with no Hazards. `realBalance.ts` has Simulations on the calm files in which every Mission Event fails or succeeds, and a plan for a Mission on the first Launch Vehicle with the first Asset. `playedStrategies.ts` has `played`, a strategy's means over 300 seeds played as in the balance runs. They're on the calm files, so they don't match the balance report. Each strategy is played once in each test file, however many tests ask for it.

A feature with new content touches these folders, in order:

1. `public/data`: the new content
2. `src/catalogue`: validating it, and `src/simulation/testCatalogue.ts` for a new Catalogue field
3. `src/simulation`: the rules, and a new format in `saveFormat.ts` for a new saved field
4. `src/balance`, for a new rule or choice: the strategies in `strategies.ts` that must cope with it, because every plan they make has to pass validation, and a check in `invalidStates.ts` for anything it makes impossible
5. `src/planning` or `src/mission`: displaying it, with styles and wiring in `src/app`, plus `src/ui/tooltips.ts` and `GLOSSARY.md` for a new game term
6. `e2e`: a browser test of the journey. A test that needs a known outcome, such as a landing that crashes or a dust storm on the second Turn, takes its seed from `e2e/seeds.ts`, which searches the real data files for one rather than pinning a number, so add a search there for a new outcome

A ticket that only changes a screen or dialog starts from its component in `src/planning`, `src/mission` or `src/save`, and usually also touches `src/ui`, the style file beside its component, such as `src/planning/planning.css`, and the `e2e` file for that subject.

A balance change starts in `public/data` and is judged by comparing `npm.cmd run balance` reports from before and after (see [Balance runs](#balance-runs)). It usually also reaches the tests of the tuned balance in `src/catalogue`, one file for each phase or post-playtest change that tuned it: `balancePhase3.test.ts`, which also holds the tests of the first Missions from before Phase 3, `balancePhase4.test.ts`, `balancePhase6.test.ts`, `balancePhase7.test.ts` and `balanceBaseFunding.test.ts`, for base funding since the Phase 7 playtest. All but Phase 3 test a strategy's means over many Programs, which they get from `src/testing/playedStrategies.ts`, so changing a strategy can break them too. It also reaches the current playtest guide's known seeds in `src/catalogue/playtestSeedsPhase7.test.ts`, the current guide in `docs/playtest`, and `src/balance/strategies.ts` if a strategy stops coping. It also reaches `e2e`: browser tests play with the real data files, so money, Public Support and Science figures in them can change with tuning, and a seed found in `e2e/seeds.ts` can change too. Rule tests in `src/simulation` use the test catalogue, so tuning doesn't touch them.

| Command                | What it does                                                   |
| ---------------------- | -------------------------------------------------------------- |
| `npm.cmd run dev`      | Starts the development server                                  |
| `npm.cmd test`         | Runs every test that doesn't need a browser                    |
| `npm.cmd run test:e2e` | Runs the browser tests, mostly at 3840×2160                    |
| `npm.cmd run verify`   | Runs every check (the canonical verification)                  |
| `npm.cmd run balance`  | Plays thousands of Programs and prints a report on the balance |

No source, test, script or style file is over 500 lines, so that each can be read whole. ESLint's `max-lines` rule enforces this for TypeScript and scripts, and CSS files keep to it by hand. It doesn't cover `package-lock.json`, the data files in `public/data`, the generated art and sounds in `public`, or Markdown. When a file nears the limit, split it at a natural seam, such as by subject for tests or by screen for styles. A new style file is imported from `src/app/main.tsx`, in cascade order.

The browser tests need Chromium, once per machine: `npx.cmd playwright install chromium`.

The sound effects in `public/sounds` are synthesised by `node scripts/generate-sounds.mjs`, and the files it makes are committed. Rerun it only to change a sound.

The Asset cards' pictures in `public/art/assets`, one for each kind of Asset and one for the Crewed Mission, are drawn from Mission Mode's own models by `node scripts/generate-asset-art.mjs`, and the files it makes are committed. It starts the development server and opens `src/mission/assetArt/assetArt.html`, a page that isn't built into the game, in Chromium for each kind, with the camera, lights and size fixed, so rerunning it gives the same files. It needs Chromium installed for the browser tests. Rerun it after changing a model; a new kind of Asset needs its model chosen in `src/mission/assetArt/AssetArt.tsx` first, and `src/planning/assetImages.test.ts` fails until its picture is made.

### The Catalogue's files

`parseCatalogue` in `catalogue.ts` checks each data file against its schema in `schemas.ts`, then runs the cross-checks, which check the files against each other, one subject per file. A new field goes in `schemas.ts`. A check that needs another file goes in the cross-check for its subject, or, for a new subject such as Technology, in a new file beside them, added to the `crossChecks` list in `catalogue.ts`.

| File                         | What it cross-checks                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `crossCheckIds.ts`           | That each id is used once in its file                                                                                                            |
| `crossCheckMissionEvents.ts` | The Mission Events that Launch Vehicles, Assets and Contingencies refer to, one Contingency per event, and each Launch Vehicle's days near Earth |
| `crossCheckHazards.ts`       | Dust storms and solar particle events against the Turn and the Trajectories                                                                      |
| `crossCheckAssets.ts`        | Assets: Mission Events that need a Landing Site, Landing Sites, Activities and Service Life                                                      |
| `crossCheckMilestones.ts`    | Milestones that can be earned, and Funding Thresholds in ascending order                                                                         |
| `crossCheckReliability.ts`   | Reliability levels in order, and Risk Bands that cover every failure probability                                                                 |
| `crossCheckTrajectories.ts`  | Trajectories and Free-returns that finish within a Turn                                                                                          |
| `crossCheckTechnology.ts`    | Technology Readiness: unproven costs and risks, Development, and ids unique across Assets and Launch Vehicles                                    |
| `crossCheckBenefits.ts`      | Benefits between Assets: that each has something to raise                                                                                        |
| `crossCheckCrew.ts`          | The Crewed Mission: its Mission Events to Mars orbit and to a Landing Site, Crew sizes in order, Activities, Health and enough names             |

### The Simulation's files

Everything outside `src/simulation` reaches the rules through `createSimulation` in `simulation.ts`. A Turn runs in this order:

1. `simulation.ts`, in `workOutTurn`, checks the plan with `planCheck.ts` and flies the Mission with `flyMission.ts`, which works out each subject of the flight in its own module: solar particle events, go/no-go checks, Contingencies, Mission Events that fail and the Crew's Health on the way.
2. `turnSteps.ts` carries out the rest of the Turn's steps, in `resolveTurn`: Milestones for arriving and for a first landing (`arrivals.ts`), technologies that became Flight-proven (`flightProven.ts`), Development started and finished (`development.ts`), Assets and Crew at work (`assetsInService.ts`, `crewAtMars.ts`), dust storms (`dustStorms.ts`), Surveys, Ongoing Research (`ongoingResearch.ts`), Science Milestones (`scienceMilestones.ts`), Funding Thresholds and the fading of Public Support. It builds the next Program, the Timeline and the Turn summary.
3. `simulation.ts` stops at the earliest Decision Point that has no answer, from the Mission or a dust storm, and gives the Timeline up to it.

Its tests go in a test file named after the rule. A new Hazard usually also needs a Decision Point kind and its answers in `types.ts`, its part of the Turn summary in `turnSummary.ts`, an entry for it in `timeline.ts`, a cautious answer in `simulation.ts`, and switching off in `calmCatalogueFiles` in `src/testing/realCatalogue.ts`, so that tests of the rest of the balance aren't disturbed by it.

### Balance runs

To check the balance without playing, run this from the repository root:

```powershell
npm.cmd run balance
```

It plays every strategy in `src/balance/strategies.ts` against the real data files, with no browser, for up to 20 Turns each on seeds 1 to 1000, and prints the report. That takes about half a minute. For a quick pass, use `npm.cmd run balance -- --programs 200`. The same command always gives the same report, so two runs can be compared line by line, for example before and after changing `public/data`. The results inform tuning and don't fail anything: the only part that can fail a build is the invalid-state test in `src/balance/balanceRuns.test.ts`, which plays a few Programs on each strategy. The command also stops with an error if a plan fails validation or a Turn leaves an invalid state.

The report starts with a summary with one row per strategy, of means per Program. Next, **Decision Points by answer** has a row for each answer each strategy gave to each kind of Decision Point, with the share of its Programs that gave it at least once and how those Programs ended. Compare two strategies that differ only in that answer, such as `steady: Soil analysis`, which shelters from dust storms, and `steady: carry on through storms`. **Technology** then covers each strategy that started a Development or flew a technology before it was Flight-proven: Developments started and finished per Program, and how Programs ended according to whether they started one, then how often each technology flew unproven, how often its first such flight failed, and how Programs ended according to whether that first flight worked. Programs that develop tend to be the ones already doing well, so compare whole strategies, such as `steady: develop the Endurance Rover when rich` with `steady: Soil analysis`, to judge a Development. **Crew** covers each strategy that flew Crew: how many of its Programs did, and over those, the Crewed Missions and Crew per Program, the Crew lost to a failed Mission Event, to Health or Supplies running out and to a solar particle event, those a Free-return brought home and those still at Mars at the end, then how Programs ended according to whether they flew Crew. Each strategy then has its own section:

- **Turn table:** one row per Turn. Everything except `Active%` is a mean over the Programs that played that Turn, at its end, so later rows only show the survivors and can rise when weaker Programs are cancelled. `Active%` is the share of all Programs still going. `Thresh$M` and `Grants$M` are that Turn's income from Funding Thresholds and Research Grants, `Thresh%` and `Grant%` are their shares of it, and `Spent$M` is the cost of Missions, Development and Upkeep.
- **Research Grants pass Funding Thresholds:** the Turn from which Research Grants pay more than Funding Thresholds in every Turn, and the Turn by which they have paid more in total, going by the Turn table's means. Either can be "never".
- **Cancelled:** how many Programs were cancelled, how many of those still had an Asset operating, and a histogram of the Turns on which that happened.
- **Funding Threshold table:** the share of Programs that reached each one, and on what Turn on average.
- **First Mission failed:** how often the first Mission failed, how often the Program could launch again on the next Turn, and whether two failures in a row cancelled it. Then how Programs ended up, in money, Science and cancellations, according to whether that first Mission worked or failed, which shows what a gamble pays.
- **Decision Points:** how many per Program of each kind, the share of Turns with at least one, and how many Contingencies ended with the Assets saved.
- **Science per Program:** what Ongoing Research earned, by Activity.

Strategies are simple on purpose, so a difference between two of them is only a rough guide to what a thoughtful player would find. Most launch whenever they can afford to, and run out of money. The ones named `steady:` play more carefully, keeping money back for a retry and keeping a few Assets at work, and each differs from `steady: Soil analysis` in one choice, so compare them with it to judge that choice. The ones named `big Program:` play as `steady: relay beside rovers` but keep up to six Assets, which one Mission a Turn holds back once a Program is rich, and differ from each other only in how they send more than one Asset at once: not at all, keeping to what is Flight-proven, on the Meridian Heavy, or on the Meridian Colossus, which needs Development. `big Program: develop the Meridian Colossus and fly Crew when rich` also sends a Crewed Mission to Mars orbit whenever it can afford one once the Meridian Colossus is Flight-proven, of the largest Crew with the most Supplies, then the most Protection, it can carry and afford, and the best Reliability it can afford, using `crewPlay.ts`, and `big Program: develop the Meridian Colossus and land Crew when rich` lands its Crew at a surveyed Landing Site once there is one. The ones named `big Program: land Crew,` differ from that one in one Crew choice: the least Supplies, no Protection, or carrying on through solar particle events with Crew aboard, except `big Program: land Crew, no Protection, least Supplies`, which makes both of the first two, to show what more Supplies are worth without Protection. The checks for invalid Crew are in `invalidCrew.ts`.

The strategies named `cautious` and `bold` are the yardsticks for how the game rewards risk: `src/catalogue/balanceBaseFunding.test.ts` holds that Cautious is rarely cancelled and recovers from a failed first Mission, and that Bold is cancelled often but is far ahead when it isn't. The play styles they and the others are built from are in `src/balance/styleParts.ts`.

To add a strategy, add an object to the `strategies` list, with no other change. Its `plan(view, tools)` sees what a player sees: the `ProgramView`, the previews and `tools.problemsWith(plan)`. It returns a `TurnPlan`, which must pass validation, so it has to cope with shortages of money and with what's on offer changing. It can also have an `answer(decisionPoint, view)` for what it does at a Decision Point, and takes the first choice offered if it hasn't. The `playStyle` helper in `src/balance/playStyle.ts` covers the common case, and pays Upkeep as `src/balance/upkeepPlay.ts` says: it keeps every Asset it can pay for, ending the missions of those with the least Service Life left when it can't, or when that frees the money for a launch while it is under its limit of Assets.

### Verification

`npm.cmd run verify` is the canonical check, and it runs in CI. It changes no tracked files, stops at the first failure, including the first failing test, and treats warning output as a failure. Run a test command directly to see every failure. In order, it runs:

1. Formatting: Prettier
2. Lint: ESLint with typescript-eslint's strict type-checked rules
3. Types: `tsc` over everything, and again over the Simulation and Catalogue with no browser or Node types
4. Static analysis: typescript-eslint's type-aware bug rules (in step 2), and Knip for unused code and dependencies
5. Tests: Vitest, then Playwright
6. Dependencies and secrets: `npm ls`, `npm audit` and Secretlint
7. Build: `vite build`

Package validation doesn't apply, because the game is private and isn't published as a package.

CI runs on pull requests and on pushes to `main`, and splits the same gates across jobs that run at the same time: one runs `npm run verify -- --without-browser-tests`, and three each run a third of the browser tests with `npm run verify -- --browser-tests-only --shard=N/3`. Together they cover every gate. Run the same options locally to repeat one job.

### Documented exceptions

- `e2e/helpers.ts` and `scripts/verify.mjs` allow one browser warning, `THREE.Clock` deprecated, because it comes from inside `@react-three/fiber`. Remove it once an upgrade stops the warning.
- `vite.config.ts` raises the chunk size warning limit to 1200 kB for the Three.js chunk, because the game runs locally (ADR 0001). Review it if the game is ever hosted.
- `knip.json` ignores `@secretlint/secretlint-rule-preset-recommend`, because only `.secretlintrc.json` uses it, by name. Review it if Secretlint's configuration moves into code.
- `package.json` overrides `minimatch` to 11.0.3, above the `^10` that ESLint and typescript-eslint ask for, because `npm audit` reports GHSA-g3hv-75wg-m249 in every version below 11.0.1. It's only used by development tools, and linting still passes. Remove it once those packages depend on a fixed version.
- `eslint.config.mjs` allows numbers in template strings, which the strict preset forbids, because Science, Public Support and day counts are shown that way and converting each one adds noise and catches nothing. Review it if numbers ever need locale formatting.
